Arquitectura de una app

Organiza tu app en View, ViewModel, Repository y Service, como en la guía de arquitectura de Flutter; el repositorio y el servicio corren en el servidor.

El ejemplo es una lista de pedidos que se pueden cancelar, escrita capa por capa en Flutter y en Thor.

Muestra los datos del ViewModel y le avisa lo que hace el usuario. No tiene lógica: lee el ViewModel y llama a sus métodos.
class OrdersView extends StatelessWidget {
  const OrdersView({super.key, required this.viewModel});

  final OrdersViewModel viewModel;

  @override

  Widget build(BuildContext context) => ListenableBuilder(
    listenable: viewModel,
    builder: (context, _) => ListView(
      children: [
        for (final order in viewModel.orders)
          ListTile(
            title: Text(order.title),
            trailing: TextButton(
              onPressed: () => viewModel.cancel.execute(order.id),

              child: const Text('Cancel'),
            ),
          ),

      ],

    ),
  );
}
class OrdersView extends StatelessWidget {
  const OrdersView({super.key, required this.viewModel});

  final OrdersViewModel viewModel;

  @override

  Widget build(BuildContext context) => Watch.list(
    viewModel.rows,
    itemKey: viewModel.keyOf,
    each: (row) => ListTile(
      title: row.text(viewModel.title),
      trailing: Watch(
        viewModel.cancelling.withArg(row.key),
        builder: (busy) => busy
            ? const Text('Cancelling…')
            : TextButton(
                // A method of the ViewModel, never a closure.
                onPressed: viewModel.cancel.run.withArg(row.key),

                child: const Text('Cancel'),
              ),
      ),
    ),
  );
}
Guarda los datos de la pantalla y las acciones que la vista puede pedir. En Thor es un ThorState: una query lee, un command cambia.
class OrdersViewModel extends ChangeNotifier {
  OrdersViewModel({required OrdersRepository ordersRepository})
    : _ordersRepository = ordersRepository {
    load = Command0(_load)..execute();
    cancel = Command1(_cancel);
  }



  final OrdersRepository _ordersRepository;



  late final Command0 load;
  late final Command1<void, String> cancel;



  List<Order> _orders = [];
  List<Order> get orders => _orders;



  Future<Result<void>> _load() async {
    final result = await _ordersRepository.list();
    switch (result) {
      case Ok<List<Order>>():
        _orders = result.value;
        notifyListeners();
        return const Result.ok(null);
      case Error<List<Order>>():
        return Result.error(result.error);

    }

  }



  Future<Result<void>> _cancel(String id) async {
    final result = await _ordersRepository.cancel(id);
    if (result is Error<void>) return result;
    return _load();
  }
}
class OrdersViewModel extends ThorState {
  // Functions of the data layer: they run on the server.
  final list = query(listOrders);



  final cancel = commandWith(
    cancelOrder,
    invalidates: (OrdersViewModel s) => [s.list],
  );



  // A state field: what the user changes in the browser.
  final onlyOpen = state(false);



  // A computed value: derived from the others, never a second list.
  late final visible = derived(
    () => [
      for (final o in list.data.value ?? const <Order>[])
        if (!onlyOpen.value || o.isOpen) o,
    ],
  );



  List<Order> rows() => visible.value;
  String keyOf(Order o) => o.id;
  String title(Order o) => o.title;
  bool cancelling(String id) => cancel.pendingFor(id);
  void setOnlyOpen(bool value) => onlyOpen.value = value;

}


final orders = OrdersViewModel();
La fuente única de los pedidos: le pide al servicio, convierte la respuesta en objetos Order y esconde de dónde vienen los datos.
abstract interface class OrdersRepository {

  Future<Result<List<Order>>> list();
  Future<Result<Order>> find(String id);
  Future<Result<void>> cancel(String id);

}


class OrdersRepositoryRemote implements OrdersRepository {
  OrdersRepositoryRemote({required OrdersService ordersService})
    : _ordersService = ordersService;



  final OrdersService _ordersService;


  @override

  Future<Result<List<Order>>> list() => _ordersService.getOrders();


  // find() and cancel() the same way…
}
abstract interface class OrdersRepository {

  Future<List<Order>> list();



  /// Throws [NotFound] when there is no such order.
  Future<Order> find(String id);
  Future<void> cancel(String id);

}


class HttpOrdersRepository implements OrdersRepository {
  HttpOrdersRepository(this._service);



  final OrdersService _service;


  @override

  Future<List<Order>> list() async {
    final json = _check(await _service.fetchAll()).json()! as List<Object?>;
    return [for (final j in json) Order.fromJson(j! as Map<String, Object?>)];
  }


  // find() and cancel() the same way…


  // The backend's errors become what a page's load can throw. Who is
  // signed in is for the middleware: a 401 stays a 401.
  ThorHttpResponse _check(ThorHttpResponse response) {
    if (response.statusCode == StatusCode.notFound) throw const NotFound();
    if (response.statusCode == StatusCode.unauthorized) throw const HttpError(StatusCode.unauthorized);
    return response.ensureOk();

  }

}

OrdersRepository get _repository => PageRequest.current.context.get(ordersKey);
Future<List<Order>> listOrders() => _repository.list();
Future<void> cancelOrder(String id) => _repository.cancel(id);
Habla con el backend y nada más. En Thor usa ThorHttpClient en el servidor.
class OrdersService {

  OrdersService(this._client, this._baseUrl);



  final http.Client _client;
  final Uri _baseUrl;



  Future<Result<List<Order>>> getOrders() async {
    try {
      final response = await _client.get(_baseUrl.resolve('orders'));
      if (response.statusCode != 200) {
        return Result.error(const HttpException('Invalid response'));
      }
      final json = jsonDecode(response.body) as List<Object?>;
      return Result.ok([
        for (final j in json) Order.fromJson(j! as Map<String, Object?>),
      ]);
    } on Exception catch (e) {
      return Result.error(e);
    }
  }



  // getOrder() and cancelOrder() the same way…

}
// One client for the whole backend: it keeps its connections open.
final _http = ThorHttpClient(
  headers: {HttpHeader.accept: 'application/json'},
  timeout: const Duration(seconds: 5),
);


class OrdersService {

  OrdersService(this._base);



  final Uri _base;



  // No state, no rules: it asks and returns the response as it is.
  Future<ThorHttpResponse> fetchAll() => _http.get(_base.resolve('orders'));



  Future<ThorHttpResponse> fetch(String id) =>
      _http.get(_base.resolve('orders/$id'));



  Future<ThorHttpResponse> cancel(String id) =>
      _http.post(_base.resolve('orders/$id/cancel'));

}

const ordersKey = ContextKey<OrdersRepository>('orders', personal: false);



// Runs before every page of the group: the repository is in the request.
Middleware provideOrders(OrdersRepository repository) => (request, next) {
  request.context.set(ordersKey, repository);
  return next();

Las capas

Cada capa de la guía de arquitectura de Flutter tiene su equivalente en Thor. La vista solo habla con su ViewModel, y el ViewModel con el repositorio.

CapaEn FlutterEn Thor
Viewun widgetun StatelessWidget
ViewModelun ChangeNotifierun ViewModel (ThorState) en el navegador; load y las acciones de la página en el servidor
Repositoryuna clase con interfazla misma clase, en el servidor
Serviceun cliente HTTP envuelto en una claseThorHttpClient envuelto en una clase, en el servidor
Dominio (opcional)casos de usofunciones o clases de Dart, cuando un ViewModel combina varios repositorios

Las tablas de recomendaciones usan los niveles de Flutter: muy recomendado, recomendado o condicional.

Separación de responsabilidades

La vista muestra datos y avisa de los eventos; el ViewModel decide qué ocurre.

// WRONG (THOR-S011): the view decides, and the closure never reaches the browser
TextButton(
  onPressed: () async {
    await cancelOrder(order.id);
    orders.list.refresh();
  },
  child: const Text('Cancel'),
)

// RIGHT: the view calls a method of its ViewModel
TextButton(
  onPressed: viewModel.cancel.run.withArg(order.id),
  child: const Text('Cancel'),
)

En Thor la separación es obligatoria: un closure que usa un ViewModel no llega al navegador (THOR-S011).

RecomendaciónNivelEn Thor
Capas de datos y de interfaz bien definidasMuy recomendadola vista y el ViewModel solo usan las funciones públicas de la capa de datos (Capa de datos)
El patrón repositoryMuy recomendadoun repositorio por tipo de dato
Views y ViewModelsMuy recomendadoun StatelessWidget y un ThorState por pantalla (Capa de interfaz)
Nada de lógica en los widgetsMuy recomendadocada callback es un método del ViewModel
ChangeNotifier y ListenableCondicionalno aplica: el navegador actualiza lo que lee Watch (Estado)
Una capa de dominioCondicionalfunciones o clases de Dart, solo si un ViewModel combina varios repositorios

Fuente única de verdad

Cada dato tiene un dueño, el repositorio. El ViewModel no guarda una copia que editar: guarda la respuesta de una query y calcula lo demás con un valor calculado (derived).

class OrdersViewModel extends ThorState {
  // The browser's only copy is the repository's last answer.
  final list = query(listOrders);

  // Computed from it, never a second list to keep in sync.
  late final count = derived(() => list.data.value?.length ?? 0);

  String countText() => '${count.value} orders';
}

final orders = OrdersViewModel();
RecomendaciónNivelEn Thor
Modelos de datos inmutablesMuy recomendadoclases con campos final y constructor const
freezed o built_valueRecomendadocualquier paquete en el servidor; lo que llega a un ViewModel es JSON con toJson y fromJson (Paquetes de pub)
Modelos de API y de dominio separadosCondicionalun fromJson en el repositorio que convierte uno en otro
El estado de una lista en la URL (solo Thor)Recomendadola búsqueda, la página y los filtros funcionan con enlaces y sin JavaScript (Servidor y acciones)

Flujo de datos unidireccional

Los datos bajan del repositorio a la vista por una query y Watch; los eventos suben de la vista al repositorio por un método del ViewModel y un command.

class OrdersViewModel extends ThorState {
  final list = query(listOrders);
  // A timer plays the server: it answers ok after 1.0 s
  final cancel = commandWith(
    cancelOrder,
    invalidates: (OrdersViewModel s) => [s.list],
  );
 
  // pending, error and result of the command
  bool busy() => cancel.pending.value;
  String failure() => cancel.error.value ?? '';
}

La interfaz es función del estado

build se ejecuta una vez, en el servidor. Un valor que cambia no se lee en build: se pasa a Watch, y el navegador actualiza ese texto.

ListenableBuilder(
  listenable: viewModel,
  builder: (context, _) => Text('${viewModel.orders.length} orders'),
)
Watch(orders.countText)
Diferencia con Flutter

El builder de Flutter se ejecuta en cada cambio. En Thor, build se ejecuta en el servidor, y leer .value ahí deja fijo el valor con el que el servidor renderizó la página (THOR-S015).

RecomendaciónNivelEn Thor
Lee .value solo en métodos del ViewModel (solo Thor)Muy recomendadobuild se ejecuta una vez, en el servidor
Una instancia final de nivel superior por ViewModel (solo Thor)Muy recomendadoel navegador arranca con esas instancias (THOR-S012)

Extensibilidad y pruebas

El repositorio es una interfaz y un middleware lo entrega a cada petición, como un Provider en Flutter. Cambiar de backend, o usar uno falso en una prueba, es cambiar el argumento del middleware.

final production = provideOrders(HttpOrdersRepository(OrdersService(apiBase)));
final inTests = provideOrders(FakeOrdersRepository());

Ni la vista ni el ViewModel saben cuál reciben. El middleware se escribe en Capa de datos y las pruebas en Pruebas.

RecomendaciónNivelEn Thor
Inyección de dependenciasMuy recomendadoun middleware y un ContextKey
Repositorios abstractosMuy recomendadoabstract interface class OrdersRepository y una implementación por entorno
Un router declarativoRecomendadoThorRouter: cada página es una URL (Rutas y navegación)
Nombres por componenteRecomendadoOrdersPage, OrdersViewModel, OrdersRepository, OrdersService
Probar cada capa sola y todas juntasMuy recomendadotest para ViewModels y repositorios; el cliente de pruebas para las páginas
Usar fakesMuy recomendadoprovideOrders(FakeOrdersRepository()) o MockTransport para el backend

Autorización

Esta recomendación no existe en Flutter, porque allí el código corre en el dispositivo del usuario. En Thor, load, las acciones y las funciones de una query o un command corren en el servidor, y cualquier usuario que abra la página puede llamarlos.

Future<List<Order>> myOrders() async {
  final context = PageRequest.current.context;
  if (context.maybeGet(currentUser) == null) {
    throw const HttpError(StatusCode.unauthorized);
  }
  return context.get(ordersKey).list();
}
Cuidado

Autoriza dentro de cada load, acción, query y command, con el usuario de la petición (Sesión y seguridad).
